# DECISIONS

Зафиксированные архитектурные и инженерные решения, принятые при разработке.

## ASR и память

**Решение:** собственный потоковый конвейер VAD → ASR на публичных `load_model` / `load_vad` / `segment_batch` / `recognize`, а не `model.with_vad(...).recognize(path)` целиком.

**Почему:** `SegmentResultsAsrAdapter.recognize()` в onnx-asr читает весь WAV в память (`read_wav_files`) и только затем начинает отдавать сегменты. Для 3-часового файла это ~690 МБ float32 плюс копии VAD. Требование ТЗ — не держать файл целиком. Поэтому:

- WAV читается блоками по `ASR_STREAM_CHUNK_S` (60 с) через `wave` + `seek`;
- Silero VAD обрабатывает блок, сегменты склеиваются на границах блоков;
- для каждого речевого сегмента из файла читается только его фрагмент;
- ASR вызывается батчами `ASR_BATCH`, память ограничена размером батча;
- прогресс: 0–10% — просканированные секунды VAD, 10–99% — конец последнего обработанного ASR-сегмента / длительность из ffprobe.

Это использует тот же публичный API onnx-asr (`load_model`, `load_vad`, `Vad.segment_batch`, `TextResultsAsrAdapter.recognize`), не дублирует декодирование и сохраняет совместимость с моделью. Альтернативный бэкенд `AutoModel.from_pretrained("ai-sage/GigaAM-v3", revision="e2e_rnnt")` не реализован: `.transcribe_longform()` требует pyannote.audio и HF-токен, а `.transcribe()` ограничен ~25 с.

## onnxruntime-gpu 1.24.4

**Решение:** фиксированная версия `onnxruntime-gpu==1.24.4`, а не `onnx-asr[gpu]` с последней ORT.

**Почему:** начиная с ORT 1.27 PyPI-пакеты собраны с CUDA 13, а база ТЗ — CUDA 12.8.1 + cuDNN 9. ORT 1.24.4 — последняя ветка с CUDA 12.8 (исключения onnx-asr: 1.24.1, 1.25.*, 1.26.0), поэтому она совместима и с базой, и с onnx-asr 0.12.0. На RTX 4070/4090/50xx CUDA 12.8 поддерживает нужные архитектуры.

## VAD

**Решение:** Silero VAD на CPU, не на GPU.

**Почему:** Silero крошечная, CPU-инференс быстрый, не занимает VRAM и не конкурирует с ASR. Параметры: threshold 0.5, min_speech 250 мс, max_speech 20 с, min_silence 300 мс, speech_pad 100 мс.

## Модели и переключение

**Решение:** кеш до 2 моделей (RNNT и CTC), загрузка по требованию, LRU-вытеснение не-default модели.

**Почему:** UI и API позволяют выбрать модель на задачу. Перезагрузка на каждый запрос запрещена; две модели GigaAM fp32 занимают ~1.8 ГБ, что комфортно для 16 ГБ. Default-модель прогревается на старте. При смене модели первый запрос ждёт загрузки; это отражено в `/api/ready`/логах.

## Очередь и события

**Решение:** SQLite в WAL + один воркер + SSE-опрос состояния из БД.

**Почему:** Redis/Celery не нужны для одной GPU-очереди. WAL позволяет web читать и писать, а worker — атомарно забирать задачу через `BEGIN IMMEDIATE ... UPDATE ... RETURNING`. SSE-эндпоинт раз в 0.75 с читает задачу и отправляет изменения; это переживает рестарт web и не требует pub/sub. Heartbeat воркера в `runtime_state` обновляется отдельным потоком, поэтому долгий ASR-батч не выглядит как зависание.

## Восстановление после рестарта

**Решение:** воркер при старте помечает `failed` все активные задачи с чужим `worker_id`; web периодически проверяет heartbeat и помечает задачи мёртвого воркера как `worker_unavailable`.

**Почему:** после `docker compose restart worker` не остаётся «вечных» `extracting/transcribing/rendering`; задача получает понятную ошибку и кнопку «Повторить». SIGTERM обрабатывается через `threading.Event`, проверяется между блоками VAD, батчами ASR и при ffmpeg; текущая задача помечается `worker_shutdown`.

## Файлы

**Решение:** исходник и WAV удаляются после успешного рендера; DOCX живёт в `/data/results/{job_id}` до TTL.

**Почему:** исходные видео могут занимать гигабайты, а для истории и повторного скачивания нужен только DOCX. TTL по умолчанию 24 ч, ручное удаление — через DELETE. Имя результата — `{stem}__{YYYY-MM-DD_HH-mm}.docx` внутри каталога задачи, что исключает коллизии и traversal.

## DOCX

**Решение:** python-docx + ручная вставка OOXML для полей `PAGE`/`NUMPAGES`, `w:lang=ru-RU` в `docDefaults` и стиле `Normal`.

**Почему:** python-docx не умеет поля страниц; без `w:lang` Word подчёркивает кириллицу. Абзацы склеиваются по паузе >1.5 с или по 6 сегментов, чтобы не было «стены текста» и строки на слово.

## Безопасность

- `AUTH_TOKEN` — общий токен, сравнение `secrets.compare_digest`; заголовки `X-Auth-Token`/`Bearer`, для SSE — `?token=`.
- Uvicorn запускается с `--no-access-log`, чтобы токен из query не попадал в access-логи; свои JSON-логи не пишут токен.
- CORS не подключён; CSP запрещает внешние ресурсы; статика только своя.
- Content-Length проверяется до чтения тела, размер — потоково при записи; reverse proxy дополнительно ограничивает 2 ГБ.
- Имена файлов санитизируются, результаты проверяются на принадлежность `DATA_DIR`.
- Non-root UID/GID 1000, `no-new-privileges`, `cap_drop: ALL`.

## Docker

- Один образ, разные `command`; GPU пробрасывается только worker через `deploy.resources.reservations.devices`.
- CPU-compose — базовый, GPU — override; `make cpu` не требует NVIDIA.
- `models-init` — профиль `init`, качает оба квантования и обе модели, чтобы volume работал в CPU и GPU и UI не зависел от сети.
- `PRELOAD_MODELS=1` кладёт веса в `/opt/models`; для air-gapped `HF_HOME=/opt/models` в `.env`.
- Тесты не попадают в runtime-образ; отдельная стадия `test` + bind-mount `tests`, поэтому `.dockerignore` может исключать тесты и медиа.
- Caddy в профиле `proxy`: TLS, basic auth, 2 ГБ body, `flush_interval -1` для SSE, `web` с `--proxy-headers`.

## Прочее

- Время в DOCX — локальное время контейнера (`TZ`, по умолчанию Europe/Moscow), с явной меткой зоны.
- `FakeTranscriber` — единственный движок для CI; реальная модель проверяется `make smoke` / `pytest -m gpu`.
- Веса не запекаются в образ по умолчанию: это экономит ~2.2 ГБ и не нарушает требование о volume. База CUDA 12.8.1 занимает ~7.3 ГБ в распакованном виде, итоговый образ без весов — ~9 ГБ uncompressed (в registry слои сжаты).
